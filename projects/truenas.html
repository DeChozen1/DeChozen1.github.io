Private Cloud Storage

Replacing cloud-storage dependence with a self-hosted Nextcloud service running on Proxmox, with HTTPS and private VPN access.

Proxmox VE Nextcloud AIO Caddy Cloudflare DNS WireGuard

Overview

The original plan was to run a virtual TrueNAS NAS for storage, backups and local file access. After troubleshooting repeated UEFI and virtual-console installation issues, the TrueNAS VM was removed and the project shifted to Nextcloud AIO for private file access, including large action-camera videos from an iPhone.

The Nextcloud AIO instance now runs in an Ubuntu Server VM on Proxmox. The existing 4TB media drive has not been reformatted or integrated into Nextcloud; its files must be preserved while the storage design is planned.

Build Log

Initial TrueNAS VM Troubleshooting

The installer first failed with a UEFI Access Denied message. Secure Boot and EFI settings were investigated, including recreating the EFI disk. A later attempt produced corrupted-looking coloured lines in the installer console, so the investigation moved to the Proxmox virtual display and serial-console settings. The VM was eventually removed and the project moved to Nextcloud AIO.

Nextcloud AIO Deployment

  • Imported and configured the Nextcloud AIO appliance in an Ubuntu Server VM on Proxmox.
  • Set the AIO data directory to /mnt/ncdata and exposed its Apache backend on port 11000 for the reverse proxy.
  • Configured the local hostname cloud.dechozen1.stream to resolve to the VM on the home network.

HTTPS, Caddy and Cloudflare DNS Challenge

  • Installed a custom Caddy build with the Cloudflare DNS provider plugin and configured Caddy to reverse-proxy requests to Nextcloud AIO.
  • Initial certificate attempts failed because the DNS provider tried to identify the zone as stream. instead of dechozen1.stream.
  • Added resolvers 1.1.1.1 to the Caddy TLS configuration. The DNS-01 challenge then succeeded and Let's Encrypt issued the certificate.
  • Caddy's systemd service still exited immediately. Troubleshooting showed /etc/caddy was root-only (700), preventing the caddy service account from reading its configuration. Changed the directory to root:caddy with mode 750, and the Caddyfile to root:caddy with mode 640. The Cloudflare token remains in a root-protected environment file loaded by systemd.
  • Confirmed Caddy listens on ports 80 and 443, while the Nextcloud AIO backend remains on 11000. HTTPS returns a redirect to the Nextcloud login page.

Private Remote Access

  • Kept the intended remote access path on the existing WireGuard VPN rather than using public port forwarding or Cloudflare Tunnel.
  • Checked the ASUS router: port forwarding is OFF, the forwarding table is empty, and DMZ is disabled.
  • Verified remote access from a phone using 4G/mobile data with the WireGuard tunnel enabled; the HTTPS Nextcloud login page loads successfully without router port forwarding.

Current Status — 11 October 2026, 1:45 PM SGT (UTC+8)

Working: Nextcloud AIO, Caddy reverse proxy, Let's Encrypt HTTPS certificate, and the Nextcloud login page at https://cloud.dechozen1.stream. Caddy is enabled as a systemd service and starts automatically.

Network posture: ASUS port forwarding is disabled and DMZ is off. The intended remote route is the existing WireGuard VPN.

Still to do: Plan how to make the existing 4TB media drive available without modifying or losing its current files.
