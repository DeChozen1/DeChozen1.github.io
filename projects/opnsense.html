OPNsense Firewall & Network

A Proxmox-hosted OPNsense transparent-bridge project focused on observing live traffic, improving network visibility and keeping the firewall path separate from host management.

OPNsense Proxmox VE Transparent Bridge DHCP Firewall Rules

Overview

The project moved from initial virtual networking design to physical passthrough and a live cable cutover. The goal is to place OPNsense transparently between the upstream modem/ONT connection and the main router so traffic can be observed and controlled without replacing the existing router's role.

Current milestone: The physical cutover has been attempted and DHCP activity has been observed on the bridge path. Management access previously became stale during the changes, and configuration adjustments were made to reduce that risk. Stable long-running operation still needs to be confirmed after these changes.

This public page deliberately omits internal IP addresses, MAC addresses, Wi-Fi identifiers, ISP account details and live firewall rules.

Logical Interface Mapping

The OPNsense VM uses three virtual interfaces, with the two bridge-facing interfaces separated from the management interface:

  • vtnet0 · modem side: connected through the Proxmox bridge assigned to the upstream physical NIC.
  • vtnet1 · router side: connected through a separate Proxmox bridge assigned to the downstream/router-facing physical NIC.
  • vtnet2 · management: connected through the host's management bridge and onboard network interface.

The intended separation is important: the two bridge-facing paths carry the traffic being inspected, while the management path should remain reachable independently during firewall changes.

Build Log and Troubleshooting

Proxmox passthrough and bridge preparation

  • Created the OPNsense VM and mapped the upstream and router-facing interfaces through separate Proxmox bridges.
  • Kept the management interface on the built-in NIC and management bridge rather than placing management access on either bridge-facing path.
  • Completed the VM-side passthrough/bridge configuration and proceeded to the physical cable cutover.

Live cutover and DHCP observations

  • Performed the physical network cutover instead of stopping at a virtual-only configuration.
  • Observed DHCP leases during the cutover, including an upstream-assigned lease appearing on the router-facing side and later changing.
  • The observed lease change was recorded as an observation, not treated as proof that the full bridge path was stable.
  • DHCP behaviour, end-to-end client connectivity and what each interface should learn from the upstream network still need a fresh check after the management changes.

Management access becoming stale

During the cutover work, the management port became unresponsive or stale. Changes were made to the configuration to prevent a repeat, but the available notes do not establish a long enough stability test to mark the issue fully resolved.

Follow-up checks should confirm management access remains reachable while traffic crosses the bridge, and that a documented recovery path is available before further live rule or interface changes.

Firewall visibility and blocklist

  • An active blocklist was created in OPNsense.
  • The next useful stage is to validate hits and firewall logs, then review whether expected devices are being logged or blocked as intended.
  • Planned learning includes inspecting traffic patterns from selected smart-home/IoT devices and applying conservative rules only after their normal behaviour has been observed.

Constraints and deferred work

  • VLAN segmentation remains constrained by the lack of a suitable managed switch in the current setup.
  • The transparent bridge should be treated as experimental until DHCP, client connectivity, management reachability and sustained throughput are reconfirmed.
  • Do not make simultaneous changes to the management path and bridge-facing firewall interfaces without a rollback plan.

Current State

  • Configured: three-interface model with distinct modem-side, router-side and management paths.
  • Attempted: physical cutover and live DHCP observation.
  • Adjusted: management-access configuration after the management port became stale.
  • Active: blocklist present, with traffic-log validation still needed.
  • Not yet confirmed: long-duration stability, final DHCP behaviour and complete validation of the rule/blocklist effect.

Next validation sequence

  1. Confirm the management interface is reachable before touching bridge-facing settings.
  2. Verify link state and expected DHCP behaviour on both sides without publishing live lease details.
  3. Test client connectivity through the existing router, then check logs for normal and blocked traffic.
  4. Run a sustained connectivity/throughput check and confirm the host management connection remains stable.
  5. Document the working configuration and recovery steps privately before introducing VLANs or more aggressive filtering.

Lessons Learned

  • Virtual interface mapping must be matched to the actual physical cable path; the VM's configuration alone does not prove the live topology.
  • Management reachability is a separate acceptance test and must be verified throughout a bridge cutover.
  • A DHCP lease changing is an observation to investigate, not enough by itself to establish whether the design is correct.
  • Blocklists should be validated against live logs before assuming that a device is being handled as intended.
  • Detailed internal addressing, interface identifiers and full rulesets belong in private operational notes, not the public portfolio.
